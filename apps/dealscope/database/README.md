## V1 boundary, design only

`initial-schema.REVIEW-ONLY.sql` is a **static proposal**. It is **not** a created migration, is **not** applied to any database and has **not** been verified by PostgreSQL, the Supabase advisor, or live cross-tenant RLS tests.

It sketches 9 database entities:
1. `ds_organizations` — verified customer business identities;
2. `ds_memberships` — user/organisation membership, role and status;
3. `ds_market_evidence` — dated and classified market/buyer evidence;
4. `ds_deal_runs` — immutable input/result snapshots and screening states;
5. `ds_offers` — customer-owned offers linked to their Deal Runs;
6. `ds_offer_disclosures` — explicit buyer disclosure records;
7. `ds_subscriptions` — provider subscription state;
8. `ds_payment_events` — deduplicated provider webhook events;
9. `ds_audit_events` — auditable actions and outcomes.

### Security baseline

- Enable RLS on **every** public table. Permit only the specified minimal **read-only** customer policies. No generic client INSERT/UPDATE/DELETE.
- Authentication is checked server-side using verified Supabase Auth identity; customer-controlled user metadata must never grant privileges.
- Tenant access depends on active `ds_memberships` records. The pure in-memory DealScope screening helper **is not** an RLS replacement.
- Offer disclosures require explicit seller consent, verified buyer tenant and release approval; **no offer/disclosure read policy** is included in the blueprint.
- Payment events and audit trails are inaccessible to browser clients through table policies. Payment provider webhooks must verify signatures, enforce unique provider event IDs and respond idempotently.
- Financial records, merchants and invoices must remain legally scoped.
- No credential, key, bank account number, private quotation, customer data or assumed organisation ID belongs in committed examples.
- Privileged server adapters must authenticate user and authorise tenant, role and operation before trusted writes; a service-role key bypassing RLS is not safe by itself.
- Verify Data API grants as well as policies. Provide multi-tenant negative tests and storage controls before release.
